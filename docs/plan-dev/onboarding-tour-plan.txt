BLUEPRINT — ONBOARDING INTERAKTIF / TOUR FITUR
=============================================================

Status: SUDAH DIIMPLEMENTASIKAN (kode selesai, `flutter analyze` bersih,
sudah dites jalan di device fisik Android — lihat CATATAN
IMPLEMENTASI di BAGIAN 3 untuk API `showcaseview` v5 yang berbeda

Ide #67 dari docs/ide-pengembangan-100.txt ("Onboarding interaktif/tour

Dokumen ini merinci scope, pendekatan teknis, dan rencana implementasi

BAGIAN 0 — SCOPE & KEPUTUSAN YANG SUDAH DIAMBIL
-----------------------------------------
Slide perkenalan yang sudah ada (lib/features/onboarding/presentation/
onboarding_page.dart) adalah carousel marketing 4 slide yang tampil
SEBELUM login/register — tidak menjelaskan elemen UI nyata di dalam
app. Fitur ini terpisah: coach-mark/spotlight yang menyorot elemen UI
sungguhan setelah user berada di Dashboard.

Keputusan (sudah dikonfirmasi, bukan open decision):
- Package: `showcaseview` — bukan hand-rolled Overlay/CustomPainter.
  App ini sengaja minim dependency (17 dependency non-dev saat ini,
  tidak ada package tutorial/coach-mark sama sekali), tapi effort
  hand-rolled spotlight+tooltip+positioning dinilai tidak sepadan untuk
  fitur ini.
- Scope v1: Dashboard (Net Worth card, grid statistik, Savings Goals
  card) + 5 ikon bottom-nav (Dashboard/Transactions/Summary/Budget/
  Profile), ditutup dengan 2 step tambahan di halaman Profile: tile
  "Atur Siklus Gajian" (Payroll) dulu, baru tile Portfolio — urutan ini
  sesuai arahan user, karena setting payroll dianggap sumber data buat
  portfolio mereka di app ini (catatan: ini keputusan urutan UX dari
  user, bukan dependency teknis yang sudah diverifikasi dari kode —
  Portfolio page tetap berfungsi walau Payroll belum di-setting).
  TIDAK masuk ke dalam tiap halaman tab lainnya (mis. tidak menyorot
  FAB "tambah transaksi" di Transactions, tidak menyorot isi halaman
  Portfolio/Payroll itu sendiri, cukup tile pintasannya di Profile) —
  itu scope v2 kalau dirasa perlu.
- Trigger: auto-tampil SEKALI per device saat user baru pertama
  mendarat di Dashboard dengan data ter-load, plus tombol manual
  "Lihat Tour Fitur" di Profile untuk mengulang kapan saja (mengabaikan
  status "sudah pernah lihat").
- Persist status "sudah pernah lihat" per-device (SharedPreferences),
  BUKAN per-akun — pola sama persis seperti OnboardingService (lihat
  BAGIAN 1).


BAGIAN 1 — INSIGHT ARSITEKTUR YANG MENYEDERHANAKAN IMPLEMENTASI
-----------------------------------------
MainShell (lib/routing/main_shell.dart) me-render `NavigationBar`
dengan 5 `NavigationDestination` sebagai sibling permanen dari
`navigationShell` (body) — BUKAN per-tab. Kelima ikon bottom-nav
SELALU ter-mount di layar terlepas dari tab mana yang aktif.

Konsekuensi: seluruh tur (3 elemen Dashboard + 5 ikon nav) bisa
dijalankan sebagai SATU `ShowCaseWidget.startShowCase()` dengan daftar
GlobalKey berurutan, tanpa logic navigasi antar-tab/route selama tur
berjalan. Tidak perlu orkestrasi "pindah tab -> tunggu frame -> mulai
showcase lagi" yang jauh lebih rawan bug. `showcaseview` juga punya
`enableAutoScroll` untuk men-scroll body Dashboard yang panjang supaya
tiap target Dashboard (mis. Savings Goals card yang mungkin di bawah
fold) otomatis masuk viewport.

Pengecualian: 2 step terakhir (Payroll & Portfolio) ada di halaman
Profile, bukan Dashboard — konten `SettingsTile` di ProfilePage cuma
ter-paint saat branch Profile aktif (beda dengan ikon nav yang selalu
ter-paint karena di luar IndexedStack). Jadi tur ini tetap butuh 1 kali
transisi navigasi: setelah step ikon nav "Profile" selesai,
TourController panggil `context.go('/profile')` supaya
StatefulShellRoute pindah ke branch Profile, tunggu 1 frame
(`addPostFrameCallback`), baru jalankan `startShowCase` gelombang kedua
untuk key Payroll lalu Portfolio. Cuma 1 transisi ini yang diperlukan
(bukan orkestrasi pindah-tab di setiap step seperti yang sebelumnya
sengaja dihindari di dokumen ini) — dan karena ProfilePage juga
`ListView` (Scrollable), `enableAutoScroll` tetap menangani posisi tile
Payroll yang cukup jauh di bawah, sama seperti pola di Dashboard.

Pola persist status yang sudah ada dan akan di-mirror:
- OnboardingService (lib/core/storage/onboarding_service.dart) — key
  SharedPreferences `has_seen_onboarding`, method `hasSeenOnboarding()`
  / `markSeen()`.
- `hasSeenOnboardingProvider` dibaca sinkron sebelum `runApp` di
  main.dart karena dipakai router redirect. Tour TIDAK butuh ini —
  tour berjalan setelah user sudah landing di /home, independen total
  dari alur redirect auth/onboarding di app_router.dart. Statusnya
  cukup dicek async di dalam DashboardPage, tidak perlu di-override di
  main.dart.


BAGIAN 2 — ALUR PENGGUNA (UX)
-----------------------------------------
1. User baru selesai register/login pertama kali -> mendarat di
   Dashboard (/home) -> setelah data dashboard selesai load (state
   `data:` pada `dashboardAsync.when`), tur otomatis mulai:
   a. Spotlight Net Worth card (kartu gradient saldo/net worth).
   b. Spotlight grid statistik (Cash Balance/Investment Balance/
      Income/Expense) sebagai satu grup, bukan 4 step terpisah.
   c. Spotlight Savings Goals card.
   d. Spotlight tiap ikon bottom-nav berurutan (Dashboard ->
      Transactions -> Summary -> Budget -> Profile), skip tab yang
      terkunci (lihat BAGIAN 4 poin 2).
   e. Setelah step d selesai, tur otomatis pindah ke halaman Profile
      (lihat BAGIAN 1 "Pengecualian") lalu spotlight tile "Atur
      Siklus Gajian" (Payroll) — dorong user setting payroll dulu.
   f. Spotlight tile Portfolio — dorong user setting/lihat portfolio
      mereka, sebagai step terakhir/penutup tur.
2. Replay manual: tile baru "Lihat Tour Fitur" di Profile -> pindah ke
   tab Dashboard -> tur mulai dari awal (mengabaikan status "sudah
   pernah lihat"), termasuk step e & f di atas.

   target yang mungkin di bawah fold — baik di Dashboard (grid
   statistik/Savings Goals card) maupun di ProfilePage (tile Payroll

   logic scroll manual sendiri.
5. Tidak ada perubahan apa pun di app_router.dart/router redirect —
   tur ini sepenuhnya independen dari alur onboarding/auth redirect

   gelombang 1 -> gelombang 2 (Dashboard -> Profile) lewat

CATATAN TEMUAN SAAT TESTING (2026-09-23)
-----------------------------------------
Saat tur otomatis dites end-to-end di device fisik (Android, akun
member premium dengan semua permission), transisi gelombang 1 ->
gelombang 2 (pindah ke halaman Profile) memicu Flutter debug
assertion yang SUDAH ADA sebelum fitur ini, BUKAN bug baru dari tur
ini:

  "ListTile background color or ink splashes may be invisible."

Ini muncul untuk SEMUA `SettingsTile` di ProfilePage (bukan cuma
Payroll/Portfolio yang baru dibungkus `Showcase`) — akar masalahnya
ada di `lib/shared/widgets/settings_tile.dart`: `SettingsTile`
membungkus `ListTile` langsung di dalam `Container(decoration:
BoxDecoration(color: ...))` tanpa `Material` widget di antaranya,
sehingga `ListTile` tidak menemukan `Material` ancestor terdekat untuk
ink splash-nya. Ini murni bug lama yang kebetulan baru "ketahuan" di
sesi testing ini karena navigasi otomatis tur adalah yang pertama kali
memaksa ProfilePage ter-build penuh dalam sesi debug tsb — assertion
ini debug-only (tidak crash, tidak muncul di release build, app tetap
jalan normal setelahnya) dan di luar scope dokumen ini. Perbaikannya
(kalau mau dikerjakan terpisah): bungkus `ListTile` di
`SettingsTile.build()` dengan `Material(color: Colors.transparent,
child: ...)` di dalam `Container` yang ada, pola serupa
`_SavingsGoalsCard` di dashboard_page.dart yang sudah pakai
`Material` + `InkWell` alih-alih `Container` + `ListTile` langsung.

Selain itu: tidak ada exception Dart lain (tidak ada duplicate
GlobalKey, null error, dsb) sepanjang sesi — build APK sukses,
`flutter analyze` bersih, app tetap responsif setelah tur berjalan.


CATATAN TEMUAN SAAT TESTING (2026-09-23, ronde 2)
-----------------------------------------
Setelah fix ronde 1 (nav icon Dashboard), tur berhasil jalan melewati
Dashboard + semua ikon nav, tapi step Payroll/Portfolio (gelombang 2)
tetap tidak pernah muncul di kedua flow (auto & tombol "Lihat Tour
Fitur"). Root cause & perbaikan di
lib/features/tour/application/tour_controller.dart:

1. Transisi gelombang 1 -> 2 sebelumnya dipicu dari `onComplete`
   dengan mencocokkan `key == tourNavProfileKey`. Masalahnya:
   `skipIfTargetNotPresent: true` (safety net dari fix ronde 1) bisa
   membuat sebuah step ter-SKIP alih-alih ter-COMPLETE — dan skip
   TIDAK memicu `onComplete` untuk key itu, jadi transisi ke gelombang
   2 tidak pernah terpicu meskipun tur kelihatan "selesai" secara
   visual. Diganti pakai `onFinish` (dipicu begitu SELURUH antrian
   `startShowCase` habis, baik lewat completed atau skip) + flag
   `_TourWave` internal supaya tetap bisa dibedakan "baru selesai
   gelombang 1" vs "baru selesai gelombang 2" (mencegah infinite loop
   kalau dipakai naif).
2. `_wave1Keys()` sebelumnya cuma baca `savingsGoalControllerProvider`
   dengan `.valueOrNull` sesaat — kalau request Savings Goals belum
   selesai (independen dari request Dashboard yang jadi trigger tur),
   step Savings Goals ke-skip diam-diam padahal user sebenarnya punya
   goals. Ditambahkan `await` ber-timeout 3 detik ke
   `savingsGoalControllerProvider.future` sebelum membentuk daftar
   key gelombang 1, kalau providernya masih loading.
3. Ditambahkan `delay: Duration(milliseconds: 250)` ke `startShowCase`
   gelombang 2, sebagai lapisan pengaman tambahan setelah
   `addPostFrameCallback` — insurance murah kalau ada race timing
   yang belum sepenuhnya dipahami di transisi pindah branch
   `StatefulShellRoute`.
4. Ditambahkan debug-only logging (`onStart`/`onComplete`/
   `onDismiss`/`onFinish`, pakai `debugLabel` tiap GlobalKey biar
   kebaca) supaya diagnosis berikutnya (kalau masih ada yang miss)
   tinggal baca log `flutter run`, tidak perlu tebak-tebak lagi.

Belum sempat re-test langsung di device fisik untuk ronde 2 ini
(device sedang dipakai user secara paralel, testing otomatis lewat
`flutter run` bentrok) — perbaikan di atas berdasarkan audit kode
menyeluruh, bukan re-verifikasi runtime. Mohon ditest ulang dari
kedua flow (auto & tombol Profile), dan kalau masih ada step yang
miss, log debug di atas akan langsung menunjukkan step mana yang
skip/tidak start.
